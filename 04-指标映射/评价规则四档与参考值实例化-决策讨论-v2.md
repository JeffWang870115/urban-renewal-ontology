### 2.2 `AssessmentRule` 是什么（答疑结论）

**结论：它是空壳，且与 `EvaluationRule` 混淆是命名历史的必然结果。**

证据链：

| 事实                                                                                | 出处                                   |
| --------------------------------------------------------------------------------- | ------------------------------------ |
| 同事本体中 `EvaluationRule` 的中文 label &#x662F;**「评价规则」**                               | `cbim_ontology(1).owl` 第 1118–1122 行 |
| 同事本体中 `AssessmentRule` 的中文 label **也是「评价规则」**（一字不差）                               | 同文件第 1130–1134 行                     |
| 同事的注释：`AssessmentRule`="多级评分/四级评价"；`EvaluationRule`="IF-THEN 阈值判定/多级评价规则"         | 同上                                   |
| 引入我方时 `AssessmentRule` 改名为"达标评价规则"，但**未留来源说明**                                    | 我方本体第 7–9 行；`类与层级.md` §2.9.3         |
| 四个规则类（EvaluationRule / AssessmentRule / WarningRule / CrossDomainRule）**实例数均为 0** | 实测本体与主 ABox                          |

**为何第一反应认为两者是同一件事**：① 同事本体里两者中文名完全相同；② 引入时改名只改代码、文档未交代；③ 两者都是零实例空壳，无可分辨的行为差异。三者叠加，混淆是必然，**不是理解问题**。

## 三、架构定稿：甲-精简版

### 3.1 决策

| 项      | 定稿                                                                                                                |
| ------ | ----------------------------------------------------------------------------------------------------------------- |
| 规则类    | **只留一个 `EvaluationRule`**（合并 `AssessmentRule` 的职责）                                                                |
| 删除的类   | `AssessmentRule`、`WarningRule`、`CrossDomainRule`（共 3 个，均空壳零实例）                                                    |
| 算法维度   | 新建受控词表类 **`EvaluationMethod`**，成员：`直接比较` / `占比化` / `均值化` / `跨域组合`（+留扩展口）                                          |
| 输出维度   | 新建受控词表类 **`EvaluationOutput`**，成员：`四级等级` / `二元预警`                                                                 |
| 规则如何表达 | 一条 `EvaluationRule` 实例：`evaluates 指标` + `evaluationMethod 词表实例` + `usesReference 参考值实例` + `evaluationOutput 词表实例` |
| 未来新增方式 | **加词表成员**（`ur:EvaluationMethod_xxx a ur:EvaluationMethod .`），不动类结构、不动属性                                           |

### 3.2 为什么不新增规则子类

- 项目已有成熟先例：`FormulaType`（7 成员）、`CollectionMethod`（9 成员）、`TreatmentType`（2 成员）均为词表实例，生成逻辑在 `_gen_ttl.py` VOCAB 字典（第 108 行）与第 411–414 行；
- 受控词表把"方式"表达为**数据**，符合"类结构只随范式变、不随方式变"的项目原则（`判定范式归纳-v1.md` 开篇）；
- 避免 `AssessmentRule`（按用途）与新子类（按算法）两组正交子类并存造成的理解负担——正是本次混淆的根源。

### 3.3 规则逻辑如何体现（三层分工）

| 层                  | 承载什么                             | 不承载什么   |
| ------------------ | -------------------------------- | ------- |
| **本体层**            | 规则元数据与参数：谁评价、什么方法、参考值多少、四档边界、实测值 | 不存可执行逻辑 |
| **约束层（SHACL）**     | 结构校验：规则须挂参考值、参考值须有来源、grade 须在四档内 | 不算等级    |
| **执行层（SPARQL/脚本）** | 真正比较：实测值 ↔ 四档区间 → 输出等级           | —       |

> 示例：指标 27 绿道覆盖率实测 65%，参考值四档边界 ≥70/60–70/50–60/<50，执行层判定为"较好"。本体只记录前三句，比较逻辑在查询里。

## 四、参考值与实测值设计（批复落实）

### 4.1 `EvaluationReference`（评价参考值）— G/H 批复

一条实例 = "某指标 + 某适用范围 + 某时期 + 一组四档边界"：

| 属性               | 含义                | 示例                                |
| ---------------- | ----------------- | --------------------------------- |
| `forIndicator`   | 指向指标              | `Indicator_27`                    |
| `appliesTo`      | 适用范围              | 全国平均 / 本省 / 同类城市                  |
| `validPeriod`    | 时期                | 十四五 / 2025                        |
| `referenceValue` | 锚点值               | 70                                |
| `ratingBand`     | **结构化四档边界**（H 批复） | 很好≥70 / 较好60–70 / 一般50–60 / 不足<50 |
| `basedOn`        | 依据来源              | Manual2026【公开】或 自评表【地方实操·待核】      |
| `direction`      | 正向/逆向             | 逆向（如 historical空置率越低越好）           |

**关键收益**：同一指标可挂多条参考值实例（全国/本省、十四五/十五五），评价时按适用范围与时期选择——即大王"不同城市不能同一而论"的本体表达。

### 4.2 `DerivedRatio`（派生比值）— I 批复

```
ur:DR_sample_I1 a ur:DerivedRatio ;
    ur:derivedFrom ur:AR_sample_I1 ;
    ur:ratioValue 7.09 ;
    ur:ratioOf "结构安全隐患住宅占比" .
```
